# Dispute evidence uploads: design

Status: awaiting approval. First of three stacked PRs (evidence, then action plan and mismatch
detection, then monitoring alerts). Branch: `feat/dispute-evidence`, based on `fix/review-hardening`.

## Why

Consumers disputing a credit record often need proof, such as a settlement letter or police report.
Today the backend can issue an upload link, but no app can use it. The system also has three defects
this work must close:

1. The letter can say "Supporting evidence is attached", yet staff cannot open the file to lodge it.
2. The server trusts client-supplied keys and never checks that a file exists.
3. Deleting a draft leaves its files in storage.

## Goals

- Consumers attach, view and remove evidence on a draft, on web and mobile.
- A file counts as evidence only after the server verifies it.
- The letter mentions evidence only when at least one verified file exists.
- Admins and compliance officers can download evidence to lodge it, with every download audited.
- Files are erased when removed, when a draft is deleted, on account erasure, and at end of retention.

## Non-goals

- Malware scanning. It depends on the AWS setup and becomes a go-live blocker (see Compliance).
- Sending files to bureaus by API. Lodging stays manual until bureau dispute APIs are contracted.
- Adding evidence after a dispute is sent.
- OCR, or checking whether a document actually supports the claim.

## Anti-goals

- A letter that claims an attachment staff cannot retrieve.
- File contents, names or storage keys in logs, events or audit payloads.
- A deletion that reports success while the file remains, with nothing retrying it.

## Approaches

1. **Evidence table plus direct-to-S3 uploads (chosen).** Reuses the existing presigned upload design,
   so services never stream file bodies, and gives each file a tracked lifecycle.
2. **Keep the `supporting_evidence` JSON array.** Smaller, but it cannot hold verification state,
   retention or retryable deletion.
3. **Proxy uploads through the gateway.** Simplifies validation, but puts 10 MB bodies through services
   that currently cap JSON at 32 KB, and works poorly on slow connections.

## Decisions made with the product owner

- Evidence is deleted **24 months after a dispute closes**, configurable through
  `EVIDENCE_RETENTION_MONTHS`, and flagged for counsel.
- Malware scanning is a go-live blocker rather than part of this PR.
- Work ships as three stacked PRs in the order above.

## Design

### Data

New migration adds `credisync.dispute_evidence`, with forced row-level security following the
`oauth_link_states` pattern (owner or system context):

| Column                                               | Notes                                                                      |
| ---------------------------------------------------- | -------------------------------------------------------------------------- |
| `id`                                                 | UUID primary key                                                           |
| `user_id`                                            | FK to users, `ON DELETE CASCADE`                                           |
| `dispute_id`                                         | FK to disputes, `ON DELETE SET NULL`, so a deletion row survives its draft |
| `storage_key`                                        | Unique, generated by the server under `uploads/<userId>/`                  |
| `content_type`                                       | `application/pdf`, `image/jpeg` or `image/png`                             |
| `size_bytes`                                         | Declared at request time, replaced by the verified size                    |
| `display_name`                                       | Sanitised original filename, max 120 characters. Never logged              |
| `status`                                             | `pending`, `verified` or `deleting`                                        |
| `created_at`, `verified_at`, `deletion_requested_at` | Timestamps                                                                 |

`supporting_evidence` is dropped, including from `db/schema.sql`. The product is pre-launch, with no
real data to migrate. `POST /disputes` stops accepting `evidenceKeys`, and
`POST /disputes/evidence-uploads` is removed. Neither has a shipped client.

### Upload flow

Evidence attaches to a saved draft, so the existing "create draft, then review" flow stays.

1. `POST /disputes/:id/evidence` with type, size and filename. Under a row lock on the draft, reject
   if the dispute is not a draft or already has 10 non-deleting files. Returns the evidence id and a
   15-minute presigned PUT.
2. The client uploads directly to S3.
3. `POST /disputes/:id/evidence/:evidenceId/complete`. The server reads the object's real size and
   first bytes and checks them against the declared type (PDF, JPEG and PNG signatures) and the 10 MB
   limit. On success the row becomes `verified` and the letter is regenerated if the
   has-evidence state changed. On failure the file is queued for deletion and the client gets a
   plain-language `invalid_evidence` error.

Submitting a draft with any `pending` file returns `409 evidence_pending`, so a letter is never sent
while an upload is unresolved.

### Other endpoints

All go through the gateway, and consumer routes are scoped by row-level security.

- `GET /disputes/:id` includes `evidence: [{id, displayName, contentType, sizeBytes, status}]`.
  Storage keys are never returned.
- `GET /disputes/:id/evidence/:evidenceId/download-url` returns a 5-minute link, for verified files.
- `DELETE /disputes/:id/evidence/:evidenceId` works on drafts only.
- `GET /admin/disputes/:id/evidence/:evidenceId/download-url` is limited to `admin` and
  `compliance_officer`, and only for submitted or later disputes.

All download links force `Content-Disposition: attachment` and `no-store`.

### Deletion

Deletion is two-phase so it can always be retried:

1. In the database transaction, mark rows `deleting`, set `deletion_requested_at`, and write the audit
   record.
2. After commit, attempt the S3 delete and remove the row. On failure the row stays `deleting`, and
   the job retries it.

Deleting a draft marks its files first, in the same transaction. Account erasure keeps its current
order: `deleteUserFiles`, then the user row.

### New `evidence` job (daily)

Added to `runner.ts`, the `all` command and `infra/terraform/schedules.tf`. It:

- retries rows in `deleting`;
- queues `pending` rows older than 24 hours;
- queues evidence on drafts untouched for 90 days, then regenerates that draft's letter;
- queues evidence on closed disputes past retention, measured from `ncr_escalated_at` if escalated,
  otherwise `resolved_at`.

Terraform also adds `expired_object_delete_marker` to the bucket lifecycle rule.

### Local development

`LocalStorageProvider` is a stub, so real flows need a real store. Add a MinIO service to the compose
stack, and an `S3_ENDPOINT` setting honoured **only** in local environments. SSE-KMS headers are
omitted when it is set. Production keeps the af-south-1 and KMS enforcement unchanged. Add an
in-memory provider for tests.

### Interfaces

- **Web:** an evidence section in `DraftReview` with file picker, per-file progress and error states,
  view, remove and retry. Must work at 360px.
- **Admin:** an evidence list with download on the dispute detail panel.
- **Mobile:** after the draft is created, a full review screen replaces the current dialog, with add
  from files or camera, remove and send. Adds `file_picker` and `image_picker`, plus camera and photo
  permission text on Android and iOS.

### Compliance

- Audit: `data_access` for consumer downloads, `admin_access` for staff downloads,
  `data_deletion_completed` with `action: delete_evidence`. POPIA erasure reports must filter this
  action, as they must `delete_draft_dispute`.
- Update `docs/legal-review-pack.md` with the 24-month period, the 90-day draft rule, and S3's up to
  7-day retention of deleted versions.
- Add **malware scanning before staff can open consumer files** as a blocker in
  `docs/go-live-checklist.md`.

## Testing

- Unit: signature checks, size limits, filename sanitising, retention date logic.
- Integration: ownership isolation, 10-file limit under concurrency, pending blocks submit, letter
  wording, staff role and audit, each deletion path, and retry after a storage failure.
- Browser, against MinIO: upload, spoofed file rejected, remove, send, staff download, draft delete
  removes the object.
- Mobile: `flutter analyze` and `flutter test`. Device camera testing is manual.

## Left to the builder

Component structure, exact error copy, job batch sizes, and the MinIO bucket bootstrap method.

## Calls made without explicit sign-off

- Evidence on drafts untouched for 90 days is deleted.
- Evidence attaches only to saved drafts, and is locked once sent.
- Retention for escalated disputes runs from the escalation date, because the system records no Ombud
  closure date.
- `supporting_evidence` and the old upload endpoint are removed rather than kept for compatibility.
- Local development gains a MinIO container.
